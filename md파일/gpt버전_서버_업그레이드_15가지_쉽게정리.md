# 서버 업그레이드 15가지 — 기능·저장 내용·파일 위치 쉽게 정리

정리 기준: 2026-10-19에 확인한 서버 코드와 현재 합의한 작업 방향입니다. 구현된 서버 기능과 아직 연결하지 않은 기능을 구분했습니다.

경로는 기본적으로 `03_Server/ProductionLine.Server/` 기준입니다. `00_Shared`, `04_Vision`으로 시작하는 경로는 전체 프로젝트 폴더 기준입니다.

## 1. DB — 사용하면서 쌓이는 정보

저장 위치: **`App_Data/productionline.db`**

총 8개 업무용 테이블에 저장합니다.

| 저장 내용 | 예시 |
|---|---|
| 사용자 (`Users`) | 아이디·이름·비밀번호 해시·관리자/작업자·활성 여부 |
| 라인 접근 권한 (`UserLineAccesses`) | worker1은 1번 라인에 접근 가능 |
| 라인 현황 (`Lines`) | 가동 상태·정상/불량/판정 불가 누적 개수 |
| 검사 결과 (`Inspections`) | 개별 검사 결과·점수·이유·검사 시각 |
| 문제 (`Issues`) | 문제 제목·설명·현재 처리 상태 |
| 상태 변경 이력 (`IssueHistories`) | 누가 언제 확인·조치·종결했는지 |
| 문의 메시지 (`IssueMessages`) | 작업자 문의·관리자 답변·작성자·시각 |
| 통신 기록 (`RequestLogs`) | 누가 무엇을 요청했고 성공·실패했는지 |

서버를 껐다 켜도 정보는 남습니다. 예전의 `data/store.json` 대신 이 DB를 사용합니다. 예전 JSON의 기록을 자동으로 가져오는 기능이 있다는 뜻은 아닙니다.

비밀번호는 원문이나 되돌려 읽는 암호문이 아니라, 비교 확인용인 **해시**로 저장합니다.

## 2. DB 자동 준비와 마이그레이션 — 서버를 켜면 정해 둔 구조대로 준비

처리 파일: **`Infrastructure/DatabaseInitializer.cs`**

- DB가 없으면 필요한 DB 파일과 테이블을 만듭니다.
- 아직 적용하지 않은 마이그레이션이 있으면 적용합니다.
- 사용자와 라인이 모두 비어 있으면 기본 관리자·작업자 계정과 라인 4개를 등록합니다.
- 이미 사용자나 라인이 있으면 기본 데이터를 다시 넣지 않습니다.

### 마이그레이션은 무엇인가요?

**마이그레이션은 DB를 만들거나 바꾸는 작업 지시서입니다.** 서버가 필요한 테이블을 스스로 생각해서 만드는 것은 아닙니다.

예를 들어 문의 메시지를 저장할 곳을 추가한다면 다음과 같습니다.

1. 클래스에 작성자·내용·시각 등 저장할 항목을 정합니다.
2. 개발자가 마이그레이션을 만들어 ‘문의 메시지 테이블을 추가해’라는 지시를 남깁니다.
3. 현재 서버는 시작할 때 그 지시 중 아직 적용하지 않은 것을 DB에 반영합니다.

쉽게 말하면 **클래스 = 정보의 모양**, **마이그레이션 = 그 모양대로 실제 DB를 바꾸는 지시서**입니다. 클래스만 수정한다고 DB 구조까지 저절로 바뀌는 것은 아닙니다.

지시서 파일은 **`Migrations/`**에 있으며 현재 변경 단계는 3개입니다.

| 이름 | 하는 일 |
|---|---|
| `InitialCreate` | 사용자·권한·라인·검사·문제·상태 이력용 기본 테이블 생성 |
| `AddIssueMessages` | 문의·답변 메시지 테이블 추가 |
| `AddRequestLogs` | 서버 요청 기록 테이블 추가 |

DB에는 어떤 마이그레이션을 적용했는지 별도 관리 기록도 남아, 이미 적용한 것은 반복 실행하지 않습니다. 이 관리 테이블은 위의 업무용 테이블 8개에 포함하지 않습니다.

### 어느 PC에 DB가 만들어지나요?

**서버를 실행한 PC에 만들어집니다. 조원의 앱을 켠다고 각 앱에 만들어지는 것은 아닙니다.**

```text
관리자 앱 ─┐
          ├→ 같은 서버 → 서버 PC의 같은 DB
사용자 앱 ─┘
```

조원이 시험하려고 자기 PC에서 서버까지 따로 실행하면 그 PC에 별도 시험용 DB가 생깁니다. 이렇게 따로 생긴 DB끼리 자동으로 합쳐지지는 않습니다. 함께 사용할 때는 두 앱이 같은 서버를 바라봐야 합니다.

현재 마이그레이션은 기존 데이터를 지우지 않고 테이블을 추가합니다. 하지만 앞으로 작성할 모든 변경의 데이터 보존까지 자동 보장되는 것은 아니므로, DB 구조를 바꾸기 전에는 변경 내용과 백업을 확인해야 합니다.

## 3. JSON — 서버 설정과 기본 매뉴얼

**`appsettings.json`**은 서버 프로젝트 바로 아래에 있는 설정 파일입니다.

- 서버가 사용할 주소·포트
- 통신 기록 보관 기간(현재 7일)
- 로그 출력 설정

설정을 바꾸면 서버를 다시 켜서 반영합니다.

**`Manuals.json`**은 AI가 참고할 기본 매뉴얼입니다. DB에 넣지 않고 JSON으로 유지하기로 했습니다. 실제 서버 내 저장 위치와 AI 코드 연결은 담당자와 별도로 확인·확정해야 합니다. 파일이 있다는 것만으로 상담 코드에 연결된 것은 아닙니다.

예전 **`data/store.json`**은 계정·검사·문제 등을 저장하던 파일이고, 현재 `AppStore`는 그 대신 SQLite DB를 사용합니다. API가 주고받는 JSON과 예전 JSON 저장 파일은 서로 다른 용도입니다.

## 4. API — 앱이 서버에 부탁하는 창구

처리 연결 파일: **`Program.cs`**

앱은 다음 일을 서버에 요청합니다.

- 로그인 확인
- 라인·검사 기록 조회
- 사용자 등록·수정
- 문제 등록·상태 변경
- 문의 보내기·답변 읽기
- AI 상담 요청

서버는 **권한 확인 → 처리·DB 저장 또는 조회 → 결과 응답**을 합니다. API는 별도 통역 프로그램이 아니라 서버에 마련된 요청 창구입니다.

```text
앱 → 서버 API로 요청 → 서버가 확인·처리 → 앱에 결과 응답
```

앱에 DB를 직접 연결해 주는 방식이 아닙니다.

## 5. 공용 코드 — 앱과 서버가 함께 쓰는 양식·함수

위치: **`00_Shared/ProductionLine.Shared/`**

| 파일 | 하는 일 |
|---|---|
| `Contracts.cs` | 주고받을 데이터의 항목과 형식 정의(DTO 등) |
| `ProductionLineApiClient.cs` | 앱에서 서버를 쉽게 호출하는 함수 모음 |

예를 들어 앱 담당자는 `LoginAsync`를 호출해 로그인하고, `SendIssueMessageAsync`를 호출해 문의를 보냅니다.

이번에는 **문의 보내기·읽기 함수와 사용자 정보 수정 함수**를 추가했습니다. 기존 공용 함수를 유지하면서 확장한 것이며, 변경된 공용 파일은 조원들도 받아야 합니다. 각자 수정한 파일을 무작정 덮어쓰지 말고 비교해서 반영해야 합니다.

## 6. 로그인·권한 — 누구이고 무엇을 할 수 있는지 확인

처리 파일: **`Infrastructure/AuthService.cs`**, **`Infrastructure/AppStore.cs`**

- 아이디·비밀번호가 맞으면 로그인 토큰을 줍니다.
- 토큰은 ‘로그인했다는 출입증’이고, 앱은 이후 요청에 붙여 보냅니다.
- 서버는 요청마다 계정 활성 여부·관리자/작업자 역할·허용 라인을 DB에서 확인합니다.
- 관리자가 권한을 바꾸거나 계정을 정지하면 다음 요청부터 반영됩니다.

토큰은 **DB가 아니라 서버 메모리**에 있고, 유효 시간은 로그인 후 8시간입니다. 서버를 다시 켜면 다시 로그인해야 합니다. 현재 별도 로그아웃 API는 없습니다.

아이디·비밀번호는 ‘누구인지’를 확인하는 용도이고, 무엇을 할 수 있는지는 계정에 저장된 역할·라인 권한으로 판단합니다. 화면에서 버튼을 숨기는 것과 별개로 서버에서도 권한을 검사합니다.

## 7. 사용자 관리 — 관리자가 작업자 정보 변경

처리 파일: **`Infrastructure/AppStore.cs`**

DB의 **`Users`**, **`UserLineAccesses`**에 반영합니다.

- 작업자 계정 등록
- 이름 변경
- 접근 가능한 라인 변경
- 계정 비활성화·재활성화
- 새 비밀번호 설정

서버 수정 기능은 기존에 있었고, 관리자 앱에서 쉽게 호출하도록 **`UpdateUserAsync`**를 추가했습니다. 화면과 버튼은 관리자 앱 담당자가 연결합니다.

작업자가 직접 회원가입하면서 관리자/작업자를 선택하는 구조는 아닙니다. 기본 계정 또는 관리자가 등록해 준 계정으로 로그인합니다.

## 8. 검사 저장 — 결과와 누적 개수 기록

판정 코드: **`04_Vision/ProductionLine.Vision/VisionInspector.cs`**  
저장 처리: **`Infrastructure/AppStore.cs`**

- 검사 한 건의 결과는 **`Inspections`**에 저장합니다.
- 정상·불량·판정 불가 누적 개수는 **`Lines`**에 반영합니다.
- 검사 결과와 누적 개수를 함께 저장합니다.

현재는 형태·색상 점수를 보내는 **시뮬레이션 검사**입니다. 판정 코드는 초기 프로젝트에 있던 기능이고, 우리는 저장을 DB에 연결했습니다. 실제 카메라·YOLO 결과 연결은 아직 별도 작업입니다.

## 9. 문제 처리 — 순서를 지키게 하기

처리 파일: **`Infrastructure/AppStore.cs`**

```text
작업자: 발생 → 확인 → 조치 중 → 완료 요청
관리자: 완료 요청 → 종결
         완료 요청 → 조치 중으로 반려(사유 필수)
```

- 순서를 건너뛰면 거절합니다.
- 같은 상태로 반복 변경할 수 없습니다.
- 작업자는 종결할 수 없습니다.
- 관리자 반려에는 사유가 필요합니다.
- 종결된 문제의 상태는 다시 바꿀 수 없습니다.

현재 상태는 **`Issues`**에 저장합니다. 초기 사용자 앱의 점검 시작은 발생 상태에서 바로 조치 중을 요청하므로 현재 서버에서 거절됩니다.

앱의 확인 처리를 추가하거나 서버의 직접 전환을 허용하는 해결 방법을 맞춰야 합니다. 확인 버튼 연결 안내는 작성했지만, 실제 조원 앱의 반영·통합 검증 여부는 별도로 확인해야 합니다. 이 문서만으로 해결 방식의 최종 결정이나 앱 수정 완료를 뜻하지 않습니다.

## 10. 상태 변경 이력 — 누가 무엇을 바꿨는지 기록

저장 위치: DB의 **`IssueHistories` 테이블**

- 관련 문제 번호
- 이전 상태·변경 후 상태
- 변경한 사용자
- 변경 시각
- 조치 메모·반려 사유

예: **‘worker1이 오전 10시에 발생 → 확인으로 변경했다.’**

현재 문제 상태와 변경 이력을 함께 저장합니다. `Issues`는 현재 모습을, `IssueHistories`는 변경 과정을 보관합니다. 거절된 요청은 상태 변경 이력이 아니라 통신 기록 대상입니다.

## 11. 문의·답변 — 작업자와 관리자 대화

저장 위치: DB의 **`IssueMessages` 테이블**

- 기존 문제에 문의·답변을 연결합니다.
- 작성자 아이디·작성 당시 이름과 역할·내용·시각을 저장합니다.
- 내용은 앞뒤 공백을 제외하고 1~2,000자입니다.
- 마지막 메시지 번호 이후의 새 메시지만 조회할 수도 있습니다.
- 해당 문제 라인에 접근할 수 있는 사용자가 이용하며, 관리자는 전체 라인에 접근할 수 있습니다.
- 종결된 문제는 읽기만 가능합니다.

**서버 API는 구현됐고, 조원들의 문의·답변 화면 연결은 별도 작업입니다.** 앱에서 몇 초마다 새 메시지를 조회하도록 연결할 수 있으며, 서버가 먼저 알려 주는 실시간 알림이나 읽음 확인 기능은 아닙니다. AI 상담 기록과도 별개입니다.

## 12. 통신 기록 — 요청이 어떻게 처리됐는지 기록

저장 위치: DB의 **`RequestLogs` 테이블**

- 요청 시각·사용자·접속 IP
- 요청한 주소·기능·관련 문제 번호
- 성공·실패 코드·처리 시간·간단한 메모

저장·변경 요청, 실패한 API 요청, 메시지가 포함된 조회 응답을 기록합니다. 비밀번호·토큰·메시지 본문은 기록하지 않습니다. 성공한 일반 조회와 새 메시지가 없는 주기적 조회는 남기지 않습니다.

**서버가 요청을 받고 어떻게 응답했는지 확인하는 근거이지, 앱 화면에 실제로 표시됐다는 증거는 아닙니다.** 서버까지 도착하지 않은 요청은 서버가 알 수 없어 보내는 PC의 기록이 따로 필요합니다.

통신 기록 저장이 실패하면 경고를 남기고 원래 요청 처리는 유지합니다. 따라서 모든 요청의 기록이 반드시 남는다고 보장하는 감사 시스템은 아닙니다.

## 13. 오래된 통신 기록 — CSV 백업 후 정리

처리 파일: **`Infrastructure/RequestLogService.cs`**  
백업 위치: **`App_Data/통신기록_백업/`**

- 서버 시작 시와 이후 하루마다 확인합니다.
- 기본 보관 기간인 7일이 지난 통신 기록을 CSV로 먼저 백업합니다.
- 백업에 성공한 기록만 DB에서 삭제합니다.
- 백업에 실패하면 삭제하지 않습니다.
- CSV에는 엑셀 수식으로 오해되지 않도록 안전 처리를 했습니다.
- 백업 파일 자체를 자동으로 삭제하는 기능은 없습니다.

백업 파일 이름 예시: **`request-logs_2026-10-19_120000.csv`**

**사용자·검사·문제·문의까지 7일 후 지우는 것이 아닙니다. 통신 기록만 정리합니다.** 서버가 꺼져 있으면 정리 작업도 실행되지 않습니다. 보관 기간은 `appsettings.json`의 `RequestLogRetentionDays`에서 바꿉니다.

## 14. 파일 관리 — 중요한 파일 구분

설정 파일: **전체 프로젝트 루트의 `.gitignore`**

- DB와 백업이 있는 `App_Data`를 Git에서 제외합니다.
- 실행 결과물인 `bin`, `obj`도 제외합니다.
- 필요한 DB 클래스가 제외되지 않도록 옛 JSON 파일 제외 규칙을 좁혔습니다.
- 일부 소스의 한글이 깨지지 않도록 UTF-8로 정리했습니다.

Git에서 제외한다는 것은 **PC에서 삭제한다는 뜻이 아닙니다.** 이미 Git에 등록된 파일이 자동으로 제거된다는 뜻도 아닙니다.

시연용 기본 비밀번호는 실제 배포·외부 공개 전에 바꿔야 합니다. 개인 DB와 비밀키·토큰을 조원 전달용 소스에 섞지 않도록 주의합니다.

- 사용자·관리자 앱 화면 연결
- AI 상담 모듈 연결과 상담 기록 저장
- YOLO 결과 형식 협의·서버 연결
- 센서 통신 방식 협의·연결
- 실제 두 PC 통신·전체 흐름 시험
- 재전송·중복 방지·연결 감시 등 추가 안정성 기능의 범위 결정

현재 요청 기록 기능이 구현됐다고 연결 끊김 감시·재전송·중복 방지까지 완성된 것은 아닙니다. AI·영상 담당의 코드 전체가 완성되지 않아도 주고받을 데이터 형식부터 합의하면 서버 작업을 이어갈 수 있습니다.
