# DB 구조 정리 — 무엇을 어디에 저장하나 (2026-10-19, 김하균)

지금 서버 코드(`03_Server/ProductionLine.Server/Data/`)를 직접 읽고 정리했습니다.
예전 문서 `DB_저장내용.md`(처음 제안), `DB_클래스_7개`, `DB_클래스_8개`를 이 문서 하나로 합쳤습니다. 예전 문서는 GitHub 기록에 남아 있습니다.

## 0. 한눈에 보기

| 저장 위치 | 무엇 | 파일 |
|---|---|---|
| **DB** (SQLite) | 사용자, 라인, 검사, 문제, 1:1 문의, 통신 기록 | `App_Data/productionline.db` |
| **JSON 파일** | 단체 채팅 (최근 5,000건) | `data/group-chat.json` |
| **JSON 파일** | AI 진단 코드만 (질문·답변 내용 없음) | `data/ai-events.jsonl` |
| **CSV 파일** | 7일 지난 통신 기록 백업 | `App_Data/통신기록_백업/` |
| 저장 안 함 | AI 상담 대화 (팀 결정) | — |
| 저장 안 함 | 로그인 출입증(토큰) — 서버 메모리에만 | — |

- 앱은 DB를 직접 만지지 않고 **서버를 통해서만** 씁니다.
- 위 파일들은 실행하면 생기는 파일이라 **GitHub에 올리지 않습니다**(`.gitignore`).
- 매뉴얼(AI가 참고하는 점검 안내)은 DB가 아니라 `05_AiAssistant/.../Manuals.json` 파일입니다.

## 1. DB 표 8개 + 관리 클래스 1개 = 클래스 9개

클래스 하나 = 표 하나, 클래스 안의 속성 하나 = 표의 칸 하나입니다.
`AppDbContext`는 표가 아니라 **표 목록과 연결 규칙을 정하는 관리 클래스**입니다.

| # | 표 | 클래스 파일 | 한 줄 설명 |
|---|---|---|---|
| 1 | `Users` | `UserEntity.cs` | 로그인 계정 |
| 2 | `UserLineAccesses` | `UserLineAccessEntity.cs` | 누가 어느 라인을 볼 수 있나 |
| 3 | `Lines` | `LineEntity.cs` | 라인 1~4의 상태와 누적 개수 |
| 4 | `Inspections` | `InspectionEntity.cs` | 검사 한 건씩의 결과 |
| 5 | `Issues` | `IssueEntity.cs` | 문제와 **지금** 상태 |
| 6 | `IssueHistories` | `IssueHistoryEntity.cs` | 문제 상태가 **바뀐 과정** |
| 7 | `IssueMessages` | `IssueMessageEntity.cs` | 문제별 작업자 문의 ↔ 관리자 답변 |
| 8 | `RequestLogs` | `RequestLogEntity.cs` | 앱↔서버 통신 기록 |
| — | (표 아님) | `AppDbContext.cs` | 표 목록, 연결 규칙, 칸 제한 |

## 2. 표마다 저장하는 칸

### ① Users — 사용자 계정
| 칸 | 뜻 |
|---|---|
| `Id` | 로그인 아이디 (예: admin, worker1). 대소문자 달라도 같은 아이디로 봄 |
| `Name` | 화면에 보일 이름 |
| `Role` | 0 관리자, 1 작업자 |
| `PasswordHash` | 비밀번호를 암호화한 값 (원래 비밀번호는 저장 안 함) |
| `IsActive` | false면 로그인·모든 요청이 바로 막힘 |

- 회원가입은 없고 **관리자가 만듭니다.** 새 계정은 항상 작업자입니다.
- 새 계정은 **단체 채팅에 자동으로 참여**합니다(채팅은 활성 계정이면 누구나 쓸 수 있음).

### ② UserLineAccesses — 라인 권한
| 칸 | 뜻 |
|---|---|
| `UserId` | Users의 아이디 |
| `LineId` | Lines의 라인 번호 |

- 한 줄 = "이 사람은 이 라인을 볼 수 있다". 라인 2개면 2줄.
- 같은 (사람, 라인)은 두 번 저장되지 않습니다.

### ③ Lines — 라인 현황
| 칸 | 뜻 |
|---|---|
| `Id` | 라인 번호 1~4 |
| `Name` | 화면에 보일 이름 |
| `IsReal` | true = 실제 라인(LINE 1만), false = 가상 데이터 |
| `OperationStatus` | 가동 상태 (예: 가동, 공정 정지) |
| `InspectionStatus` | 검사 상태 (예: 검사 중, 검사 확인 필요) |
| `NormalCount` / `DefectCount` / `UndeterminedCount` | 정상 / 불량 / 판정 불가 누적 개수 |
| `UpdatedAt` | 마지막으로 바뀐 시각 |

### ④ Inspections — 검사 결과 한 건
| 칸 | 뜻 |
|---|---|
| `Id` | 검사 고유 번호 |
| `LineId` | 어느 라인 |
| `Result` | 0 정상, 1 불량, 2 판정 불가 |
| `ShapeScore` / `ColorScore` | 형태 / 색상 점수 (0~1) |
| `Reason` | 판정 이유 |
| `InspectedAt` | 검사 시각 |

- 검사를 저장할 때 Lines의 누적 개수도 같이 1 올립니다.
- 지금은 점수를 받아 판정하는 **시뮬레이션**입니다. YOLO 결과 형식이 정해지면 칸이 늘어날 수 있습니다.

### ⑤ Issues — 문제와 지금 상태
| 칸 | 뜻 |
|---|---|
| `Id` | 문제 고유 번호 |
| `LineId` | 어느 라인 |
| `Type` | 0 생산라인 문제, 1 검사 시스템 문제 |
| `Title` / `Description` | 제목 / 설명 |
| `Status` | 0 발생, 1 확인, 2 조치 중, 3 완료 요청, 4 종결 |
| `CreatedBy` | 등록한 사람 아이디 |
| `ActionNote` | 마지막 조치 메모 (반려하면 반려 사유) |
| `CreatedAt` / `UpdatedAt` | 등록 / 마지막 변경 시각 |

- 상태 순서(안 A): 작업자 발생→확인→조치 중→완료 요청, 관리자 완료 요청→종결 또는 →조치 중(반려, 사유 필수).
- 순서 검사는 `Infrastructure/AppStore.cs`가 합니다. 어기면 409.

### ⑥ IssueHistories — 상태 변경 기록
| 칸 | 뜻 |
|---|---|
| `Id` | 기록 번호 |
| `IssueId` | 어떤 문제 |
| `PreviousStatus` → `NewStatus` | 무엇에서 무엇으로 |
| `ChangedBy` | 바꾼 사람 (로그인 계정으로 서버가 정함) |
| `ChangedAt` | 바꾼 시각 |
| `ActionNote` | 조치 내용 또는 반려 사유 |

- Issues의 상태 변경과 **한 번에 같이** 저장합니다. 거절된 요청은 남지 않습니다.
- 앱에서 이 기록을 볼 창구는 아직 없습니다(DB에만 있음).

### ⑦ IssueMessages — 1:1 문의 메시지
| 칸 | 뜻 |
|---|---|
| `Id` | 메시지 번호 (1, 2, 3… 이 순서 = 보낸 순서) |
| `IssueId` | 어떤 문제에 대한 메시지 |
| `SenderId` / `SenderName` / `SenderRole` | 보낸 사람, 보낸 당시 이름·역할 |
| `Message` | 내용 1~2,000자 |
| `CreatedAt` | 보낸 시각 |

- 앱은 5초마다 "마지막 번호 다음 것만" 물어봅니다. 종결된 문제는 읽기만 됩니다.
- **단체 채팅이나 AI 상담과는 다른 것**입니다.

### ⑧ RequestLogs — 통신 기록
| 칸 | 뜻 |
|---|---|
| `Id` | 기록 번호 |
| `ReceivedAt` | 서버가 받은 시각 |
| `UserId` / `ClientIp` | 요청한 사람 / PC 주소 |
| `Method` / `Path` / `Action` | GET·POST·PUT / 주소 / 기능 이름(예: 메시지 보내기) |
| `IssueId` | 관련 문제 번호 (없으면 비어 있음) |
| `StatusCode` / `DurationMs` | 결과 번호 / 걸린 시간 |
| `Note` | 메모 (예: "메시지 12번 저장") |

- 남기는 것: 저장·변경 요청, 실패한 요청, 새 메시지를 응답한 조회.
- 남기지 않는 것: 비밀번호, 토큰, 메시지 내용, 평범한 조회(채팅 2초 확인 포함).
- 7일 지나면 CSV로 백업하고 지웁니다(`appsettings.json`의 `RequestLogRetentionDays`).
- 없는 사용자·문제로 온 요청도 남겨야 해서 다른 표와 **연결(외래 키)을 걸지 않았습니다.**

## 3. 표끼리의 연결 (AppDbContext)

```
Users ──< UserLineAccesses >── Lines
                                 │
                 ┌───────────────┼──────────────┐
            Inspections        Issues ──< IssueHistories
                                 │
                            IssueMessages
RequestLogs (연결 없음)
```

- `──<` = 하나에 여러 개 (라인 하나에 검사 여러 개)
- **삭제 제한(Restrict):** 연결된 기록이 있는 사용자·라인·문제는 함부로 지울 수 없습니다. 기록 보존을 위해서입니다.
- 시각 칸 일부는 SQLite에서 정렬이 되도록 큰 숫자(Ticks)로 저장합니다.

## 4. DB를 준비하는 코드

| 파일 | 하는 일 |
|---|---|
| `Infrastructure/DatabaseInitializer.cs` | 서버가 켜질 때 표를 만들거나 새 설계도를 자동 적용. 비어 있으면 기본 데이터(admin, worker1, 라인 4개) 넣기 |
| `Migrations/` | 표 설계도 3개: `InitialCreate`, `AddIssueMessages`, `AddRequestLogs` |
| `Infrastructure/AppStore.cs` | 조회·저장, 상태 순서 검사 |
| `Infrastructure/AuthService.cs` | 출입증 발급, 요청마다 DB에서 활성 여부·권한 다시 확인 |

**표 모양을 바꿀 때:** `Data` 클래스를 고친 뒤 새 마이그레이션을 만들어야 DB에 반영됩니다. 중요한 DB는 먼저 복사해 두세요.

## 5. 아직 DB에 없는 것

- 센서(아두이노) 값 — 센서가 확정되면 표 추가
- YOLO 검사 결과 전용 칸 — 형식이 정해지면 Inspections에 칸 추가
- 같은 검사 결과가 두 번 와도 한 번만 저장하는 요청 번호
- AI 상담 기록 — **저장 안 하기로 결정** (10-19)
