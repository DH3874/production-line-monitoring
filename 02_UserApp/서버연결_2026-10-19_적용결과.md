# 2026-10-18 서버 안내 적용 결과 (2026-10-19)

## 적용한 근거와 범위

- 제공 문서: 바탕화면 `조원_전달_2026-10-18.md`, `사용자앱_확인버튼추가_서버연결안내.md`.
- 대상: 기존에 작업한 `02_UserApp_장서진_수정본` 사용자 앱. 디자인·카메라·AI 화면은 유지.
- 관리자 앱, 서버, DB, 공용 enum/DTO/HTTP 클라이언트 소스는 변경하지 않음.

## 완료한 변경

- 작업자는 `Occurred → Acknowledged → InProgress → CompletionRequested`만 요청. 이전에 허용했던 `InProgress → InProgress` 조치 메모 저장을 제거.
- 확인/점검 시작 버튼은 해당 단계에서만 활성화. 확인은 `사용자가 문제를 확인함`, 점검 시작은 `사용자가 점검을 시작함`을 기존 UpdateIssueAsync로 전송.
- 완료 요청만 실제 입력한 조치 내용을 사용하며 성공 후 입력 초기화. 확인·점검 시작은 작성 중인 완료 메모를 지우지 않음.
- 요청 중 중복 실행 차단. 변경 전 자동 조회가 진행 중이면 기다린 뒤 다시 조회해 변경 후 새로고침이 생략되지 않도록 함. 문제 선택 ID 유지.
- 반려로 조치 중 상태가 반환되면 ActionNote의 사유를 표시하고 재완료 요청 허용. 점검 시작을 다시 전송하지 않음.
- 상태 요청 실패 시 서버 안내를 표시하고 상태를 재조회하며, 변경 요청을 자동 재전송하지 않음. 입력 보존. 알려진 인증 만료 응답은 로그인 화면으로 복귀하고 카메라 검사를 중지.
- 새 메시지 함수가 없는 현재 공용 코드로 문의 버튼을 누르면 새 문제를 만드는 이전 동작 제거. 관리자 보내기 버튼 비활성화 및 연결 준비 안내. 종결 문제는 관리자 입력도 읽기 전용. 입력 길이 제한 2,000자.
- 기존 로컬 관리자 대화 기록은 파일에서 삭제하지 않지만, 서버 메시지나 관리자 답장으로 표시하지 않음. AI 대화는 기존 로컬 저장 유지.

## 관리자 메시지 연결에 필요한 파일 (미전달)

현재 작업 폴더와 바탕화면의 다른 프로젝트 복사본을 확인했으나, 두 곳 모두 다음 신규 함수가 없습니다.

- `SendIssueMessageAsync(문제번호, 내용)`
- `GetIssueMessagesAsync(문제번호)`
- `GetIssueMessagesAsync(문제번호, 마지막메시지번호)`
- `UpdateUserAsync(아이디, UpdateUserRequest)`

따라서 김하균 담당이 수정한 다음 **실제 최신 소스**를 받아야 합니다.

1. `00_Shared/ProductionLine.Shared/Contracts.cs`
2. `00_Shared/ProductionLine.Shared/ProductionLineApiClient.cs`

문서에는 메시지 응답 DTO의 필드·Id 자료형·예외 상태 코드 보존 방식·엔드포인트가 명시되지 않았습니다. 임의 DTO/URL/인증 구조를 만들지 않았습니다. 관리자 메시지 송수신과 5초 증분 폴링은 아직 적용 완료가 아닙니다. 메시지 타이머만 빈 상태로 실행하지 않습니다.

현재 공용 클라이언트는 HTTP 코드를 예외에 보존하지 않아 서버 메시지가 같지 않으면 401을 완전히 구분할 수 없습니다. 현재 서버의 정확한 `로그인이 필요합니다.` 또는 HttpRequestException의 401만 인식합니다. 모든 최신 인증 오류 분기는 실제 공용 클라이언트를 받은 후 재확인해야 합니다.

## 김하균에게 전달할 연결 정보

- 주소는 기존 생성자 인수 → PRODUCTIONLINE_SERVER_URL → http://127.0.0.1:5050 순서 유지. 실제 서버 PC IP는 미확정, 포트 5050 유지.
- 현재 상태 변경 입력: 문제 Guid, 기존 IssueStatus 값 1/2/3, 새 actionNote. 수행자·시각·이력은 서버 처리. 응답 IssueDto 유지.
- 메시지 연결 예정: 문제 선택 시 전체 조회, 문제별 마지막 메시지 ID 보관, 별도 WinForms Timer(5000ms)로 증분 조회. 중복 ID 제거, 문제 변경 중 도착한 응답을 다른 문제에 섞지 않기. 종결 문제는 조회만 허용. AI 기록과 분리.
- 메시지 전송은 현재 문제에만 하며 새 문제 등록 호출을 하지 않음. 400/403 안내, 404 목록 갱신, 409 최신 상태 갱신, 401 재로그인 처리는 최신 공용 예외 규격에 맞춰 마무리 필요.

## 검증 결과와 한계

- 별도 로컬 테스트 서버에서 단일 단계만 허용하는 409 규칙을 적용해 UI를 검사.
- 확인 전 완료 요청 차단, 확인·점검 시작 기본 메모, 동일 상태 요청 차단, 완료 조치 내용 전송, 실패 시 입력 유지, 관리자 반려 후 재완료, 종결 후 편집 차단 검증 통과.
- 다른 PC가 먼저 확인한 상황을 모의해 409 후 최신 상태 재조회 및 입력 유지 검증. 404 후 사라진 문제 제거·버튼 비활성화, 현재 알려진 401 응답 후 로그인 복귀 검증.
- 최신 메시지 클라이언트가 없는 경우 새 문제가 생성되지 않는지 검증. 기존 AI 대화 복원과 합성 카메라 분석 흐름 회귀 검사 통과.
- 실제 10월 18일 신규 서버·SQLite·관리자 답장·두 PC 통합 시험은 미실행. 공용 최신 파일과 실제 서버 전달 후 별도 필요. 물리 카메라 수신은 장치 열기 실패로 미검증.
- 변경 파일: UserMainForm.cs, Form1.cs, ServerNoticeIntegration.cs, Verification/FunctionalChecks.cs, 구현안내.md, 이 문서.
